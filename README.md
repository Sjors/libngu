## Primitives

- using [libsecp256k1](https://github.com/bitcoin-core/secp256k1) for everything, except:
- [mbedtls](https://github.com/ARMmbed/mbedtls) if already present on target (ESP32 uses for TLS)
- otherwise use [cifra](https://github.com/ctz/cifra)
- generic EC, certificates stuff, disabled if no mbedtls
- AES submodule disabled if you have mbedtls, because ucryptolib is same
- libwally-core used for testing only

## Install

- `make one-time` does submodule bullshit, configures K1 lib
- `make quick` compiles Unix micropython port, runs tests
- can play with `./ngu-micropython` binary on your desktop
- ESP32 builds stop until the integrator attests that true entropy stays
  active whenever `ngu.random` is used (see below). Once that is established,
  compile and burn onto the TTGO board:
```
make -f makefile.esp32
make -f makefile.esp32 deploy
```
- on target, do:
```
>>> import ngu_tests.run
```
or for single test:
```
>>> import ngu_tests.test_hash
```

- STM32 port builds, but untested:
```
make -f makefile.stm32 
```

## Random number integration

`ngu.random` uses Cifra Hash_DRBG, initially seeded with 128 bytes from the
target entropy source. Generated bytes are also XORed with fresh source words.
There is no software fallback:

- STM32 uses `rng_get()` only when the board enables MicroPython's hardware RNG
  with `MICROPY_HW_ENABLE_RNG=1`, or supplies an external implementation and
  sets `NGU_STM32_EXTERNAL_RNG_GET=1`. Without either source, the build fails. A
  zero word is rejected; MicroPython's STM32 implementation uses zero to report
  a peripheral timeout.
- ESP32 uses `esp_random()` only when the build sets
  `NGU_ESP32_RNG_IS_TRUE_RANDOM=1`. This is the integrator's attestation that a
  true entropy source remains active whenever random data is requested. Without
  active RF or another enabled entropy source, ESP-IDF documents the output as
  pseudo-random. See the [ESP-IDF RNG documentation](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/random.html).
- macOS and FreeBSD use `arc4random()`. Linux uses `getrandom(2)`. Unknown
  targets fail to build.

The runtime rejects zero and an immediate repeated word. This is a narrow
failure check, not a substitute for validating the raw entropy source on each
hardware target.

`ngu.random.reseed()` accepts bytes-like values of at least 32 bytes and mixes
them into the existing state. The module keeps mutable DRBG and source-check
state, so calls must be serialized. Python calls require the VM's GIL when
threads are enabled; direct C callers own that synchronization.

## Experimental interactive Schnorr anti-exfil

Enable `NGU_INCL_SCHNORR=1` (or `NGU_INCL_MUSIG=1`) when building.
The anti-exfil API is omitted when Schnorr support is disabled.

`ngu.secp256k1.anti_exfil_commit(keypair, message32, commitment32)` returns
the full 33-byte compressed original nonce. It does not return a signature.
`anti_exfil_sign(keypair, message32, commitment32, nonce33, entropy32)`
checks both supplied commitment fields, applies the host's nonzero scalar,
and verifies the resulting BIP340 signature before returning its 64 bytes.
Pass the actual signing keypair, including the Taproot tweak for key-path
signing. Both calls use the same keypair and message.

This implements the draft BIP-EXFIL single-signer protocol; the two hash tags
are provisional and vectors must be regenerated after BIP tag assignment.
It is separate from ordinary BIP340 signing, whose nonce derivation must not
be reused for this additive protocol. The host must independently check the
signature and the relation to its originally recorded nonce. After receiving
a nonce, a retry must reuse the same transcript rather than fresh entropy.
Neither round's transcript belongs in transaction metadata or diagnostic logs.

The shared eight-vector test is `ngu/ngu_tests/test_anti_exfil.py`; run it
with the native MicroPython build that includes ngu. No secret scalar
operations are performed in MicroPython. This experimental implementation
has not received cryptographic review.
